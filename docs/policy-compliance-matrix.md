# SAKAY Policy Compliance Matrix

This document tracks system-wide compliance against *Appendix B - Operational Policies and Business Rules* for the SAKAY ride-hailing platform (Calapan City, Oriental Mindoro).

---

## 1. Compliance Status Legend

- **`[OK]`**: Implemented AND verified by reading the authoritative code path (cite exact file path, function/component name, line range, and enforcement logic).
- **`[PARTIAL]`**: Exists but incomplete, incorrect, UI-only, client-side only, or non-authoritative (state what is missing).
- **`[MISSING]`**: Not implemented anywhere in the repository.
- **`[CONFLICT]`**: Implemented differently from the policy, or two implementations/specifications disagree.
- **`[UNKNOWN]`**: Cannot be determined from the repository.

## 9. Security Patch SP-1: Fail-Closed Trust Checks (affects Batches 3, 4 and 5)

**Status: migration `20261007000004_security_null_safe_service_context.sql` written; verified in fresh database sessions and by a rolled-back dry run on the hosted database; NOT yet applied there (apply with `node scripts/applySecurityPatch.js apply`). Decisions and the full explanation: `docs/policy-decisions.md` section 7.5.**

Batch 3's `is_service_context()` answered NULL (not FALSE) in a database session that had never set `sakay.internal_context`, so every guard written `IF NOT is_service_context()` skipped its protection in such a session (for example a freshly opened pooled connection). The patch makes the helper strictly TRUE or FALSE and replaces the one inline copy of the check.

**How these statuses were verified**
- **Executed:** `node scripts/db-tests/security/null-safe-service-context.js` (39 checks). Each probe runs on its own brand-new backend (the populated database is dumped and loaded into a new PGlite instance, so the setting was never defined). Before the patch every attack works (the flaw is reproduced); after it every attack is refused and the legitimate paths still work. It also shows why nothing caught it earlier: in a session that had already defined the setting, the old guard holds.
- **Regression:** `node scripts/db-tests/run-all.js` 20 suites, 650 checks, 0 failed; the Batch 4 suites on the full chain (171 checks); the Batch 3 suites foundation, engine, exemptions and guards on the full chain (168 checks).
- **Live dry run (rolled back):** `node scripts/applySecurityPatch.js dryrun` on the hosted database: today 8 of 8 probed attacks work in brand-new connections; with the patch all 8 are refused and the legitimate paths still work; afterwards nothing was kept (the helper still answers NULL, the patch is not in the migration history).
